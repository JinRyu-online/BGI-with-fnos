# 定时任务功能开发计划（feat/scheduled-tasks）

> 2026-09-05 起草 · 经 subagent 架构评审修订（吸收 6 条必须修改点）
> 背景：原神矿物 48h/魔晶矿 72h 刷新、世界怪物与每日以**凌晨 4 点**为界刷新；
> 需要"每周一/周四 12:00 唤醒 PC → 挖矿一条龙 → 完成后自动休眠"这类定时执行。

## 0. 需求与刷新机制依据

| 资源 | 刷新周期 | 界 |
|---|---|---|
| 水晶块等普通矿 | ~48h（2 天） | 采集时刻起算 |
| 魔晶矿 | ~72h（3 天） | 采集时刻起算 |
| 世界怪物/精英怪素材 | 每日 | 凌晨 4:00（服务器日界） |
| 每日委托/树脂/洞天宝钱 | 每日 | 凌晨 4:00 |

⇒ 调度模型只需「周几 + 时刻」，不需要复杂 cron；凌晨 4 点后跑当日、12:00 跑午间都是典型窗口。

## 1. 架构决策

**调度放 NAS 端**（评审确认）：WOL 能唤醒关机 PC，Windows 任务计划程序在 S5 关机态唤不醒且会绕过 listener 单槽状态机（NAS 看不到任务/无历史/无日志）。NAS=大脑，Windows=执行器，与现有职责划分一致。

**自写轻量调度循环**（不引 APScheduler）：与现有 reconcile 线程同款 `threading.Event.wait()` 模式，零新依赖，测试友好。

## 2. 核心设计

### 2.1 数据结构

config.json 新增（`Settings._deep_merge` 对 list 整体覆盖，天然兼容）：
```json
"schedules": [
  {
    "id": "s-1712345678",
    "enabled": true,
    "name": "挖矿一条龙",
    "time": "12:00",
    "weekdays": [1, 4],
    "task_id": "mining_all",
    "wake": true,
    "wake_timeout_sec": 300,
    "skip_if_busy": true
  }
]
```
- `weekdays` ISO 语义 **0=周一**；`[]` 或不填 = 每天
- `wake=false` 时不发 WOL（PC 常开场景），仅触发
- 不加 timeout_min 覆盖（任务超时唯一来源是 Windows tasks.json，避免两处打架）

运行状态独立文件 `BGI_DATA_DIR/schedules_state.json`（**绝不放 config.json**——`Settings.save` 整文件覆盖无锁，与 API 线程并发写会互丢）：
```json
{ "s-1712345678": { "last_fired_at": 1757000000, "last_job_id": "j-xxx", "last_result": "triggered|skipped_busy|wake_timeout|task_not_found|error:...", "last_error": null } }
```
新组件 `ScheduleStateStore`（仿 HistoryStore：独立 JSON + threading.Lock + 原子写）。

### 2.2 调度器（main.py）

- `next_fire_at(now, time_hhmm, weekdays)` **纯函数**（now 显式入参，绝不内部调 datetime.now()；naive 本地时间语义，容器 TZ=Asia/Shanghai）
- `Scheduler.tick(now)` 同步方法：读 schedules → 找到期（`last_fired_at < fire_window_start <= now`，防 30s 内二次触发）→ **同 tick 多条到期只投第一条**，其余标 skipped_conflict → 每条投给独立 worker 线程
- **tick 与执行链分离**（评审必须项）：唤醒→轮询 /health 最长 5 分钟是阻塞操作，绝不能卡 30s 循环
- 执行链（worker 内，全部可注入）：先探 `/health`（PC 已醒则跳过 WOL+等待）→ 需要则 `send_magic_packet` ×3（连发抗丢包）→ 轮询 /health 直至就绪或 wake_timeout → 404 时重试一次（listener 刚启动 TaskRegistry 热加载未完）→ `client.trigger(task_id)`
- 失败分支：409（Windows 忙）→ skipped_busy 落记录，**禁止排队**；wake 超时 → wake_timeout；task 404 二次仍失败 → task_not_found
- 防重入 + 补跑语义：`last_fired_at` 持久化；**错过超 5 分钟宽容窗即跳过仅记录**（不做 catch-up，避免半夜突然开机惊吓）
- 触发成功 `history.record({..., "schedule_id": id})`；**history.py `prev_fields_fallback` 字段集必须补 `schedule_id`**（否则 reconcile 落终态时溯源丢失——评审发现的既有代码坑）

### 2.3 API

- `GET /api/schedules`（含后端算好的 `next_fire_at`，前端不自算）
- `PUT /api/schedules`（整体替换，带校验：time 格式/weekdays 范围/task_id 存在性软校验——Windows 离线不阻断保存）
- `DELETE /api/schedules/{id}`（顺手清 state 残留）
- `POST /api/schedules/{id}/run` 手动立即执行（与定时共用执行链，复用防重入标记）
- `create_app(..., scheduler_interval=30.0, wake_fn=None, scheduler_factory=None)` 注入参数（对称 reconciler_factory 先例），0=禁用

### 2.4 时区（评审高危项）

Dockerfile：`RUN apt-get update && apt-get install -y --no-install-recommends tzdata` + `ENV TZ=Asia/Shanghai`。**slim 镜像无 tzdata，仅设 TZ 环境变量不生效**（差 8 小时=矿物窗口全错）。M1 验收：容器内 `date` 显示 CST + 启动日志打印 `time.localtime()` 自检。

### 2.5 前端

- **独立页** `/schedules`（底部第 5 个 tab；设置页已有 4 区块且扫描展开很长，内联会失控）
- 页面结构：列表卡（名称/时间/星期 chips/启停开关/下次触发时间/上次结果徽章）+ 新增编辑弹层 + 危险操作删除确认（复用 showConfirm）
- types.ts 加 `ScheduleInfo`；useApi.ts 加 5 个方法；constants.ts 加星期文案与 last_result 文案（单一来源约定）；mock/server.ts 同步
- HistoryPage：schedule_id 记录加"定时"徽章

## 3. 测试计划

- 纯函数 `next_fire_at`/到期判定：无 IO 单测（含跨日、周日、非法输入）
- `Scheduler.tick(now)` 直接单测：防重入、双条冲突、超窗跳过（不启线程）
- 执行链：fake client_factory（health/trigger 可编程）+ wake_fn 注入 + `mock.patch("wol.send_magic_packet")`（照 test_wol 先例）
- 线程集成：`with TestClient(app)` + `_wait_until`（照 test_reconcile 范式，短 interval）
- 新增 ≥15 用例；回归 test_settings.py 的 DEFAULT_CONFIG 键集合断言需加 `schedules`

## 5. 风险清单（评审后）

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| slim 镜像无 tzdata，触发偏 8h | 高 | 高 | 显式安装 tzdata + 验收容器 date |
| WOL 实际唤不醒（BIOS/广播被丢） | 中 | 高 | 连发 3 包；可配定向子网广播；真机先验证一次 |
| Settings.save 并发覆盖 | 中 | 高 | 状态独立文件（已采纳） |
| 409 处理不当重复触发 | 中 | 中 | skip_if_busy 跳过语义 + 单测 |
| 执行链堵调度循环 | 中 | 中 | tick/worker 分离（已采纳） |
| 任务 failed 后 PC 整夜不睡 | 中 | 中 | state 落 last_result + UI 标注（Windows 端只有 done 才 after_done，属既有行为，第一版只在 UI 提示） |
| task_id 失效 | 低-中 | 中 | 保存软校验 + 触发 404 落记录 |

## 6. 明确不做（第一版）

- 通知推送（fnOS 通知渠道接入留待后续；先用 last_result + 历史徽章）
- 每月/每年调度、多任务串行队列、catch-up 补跑、timeout_min 覆盖
